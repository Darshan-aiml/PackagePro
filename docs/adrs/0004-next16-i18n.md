# 0004 — i18n: next-intl v4 inside Next.js 16 (Turbopack)

**Status:** adopted

## Context

Three locales (`en`, `hi`, `ta`) must render identical flows, and the product must
survive Next 16's renamed middleware and Turbopack's stricter module resolution.

## Decision

- **Routing**: `src/i18n/routing.ts` (`defineRouting`), `src/i18n/navigation.ts`
  (`createNavigation` exports typed `Link`, `usePathname`, …), `src/proxy.ts` — Next 16
  renamed `middleware.ts` to `proxy.ts`; the middleware config lives there using
  `createMiddleware` (convention verified against the installed package).
- **Config**: `createNextIntlPlugin("./src/i18n/request.ts")` wired into
  `next.config.ts`. Auto-discovery of `src/i18n/request.ts` fails under Turbopack's
  build-time resolution, and the production placeholder throws the "Couldn't find
  next-intl config file" error — the explicit plugin path is what fixed the build.
- **Messages**: `src/messages/{en,hi,ta}.json` imported through a static map
  (`messages/index.ts`). Turbopack can't statically resolve `await import(…/locale.json)`
  dynamic fragments, and cross-directory JSON imports from the config hook were flaky;
  a single `import` at the top of `index.ts` is deterministic. Key sets are asserted
  identical by `src/messages/parity.test.ts`.

## Consequences

- Routes: `/{locale}`, `/{locale}/packages/[packageId]`, `/{locale}/plan`, with the
  proxy feeding the locale out of the path/accept-header.
- All user-facing strings go through `useTranslations`/`getTranslations`; the engines
  never see locale-aware text (reason *keys* are stable across locales).
- Build output shows `ƒ Proxy (Middleware)` and all three locale roots render 200 in
  both dev and production builds.
